# fsm-lab — the long-running agent orchestration substrate (project brief)

This repo runs a finite-state machine that orchestrates worker agents on
GitHub Actions: state lives on the `fsm-state` branch (state.json +
append-only journals), the conductor self-chains turns via
repository_dispatch, workers execute tasks and report five-class outcomes,
and a watchdog backstops chain death. It is the reference implementation of
the worker-turn contract (T46/W-B).

## The contract (how a turn works)

- Every dispatch carries an ENVELOPE: `{task_ref, prompt, deadline_ms,
  session, budget{max_turns, wall_ms, lane_attempts}, mode, attempt}`.
  The prompt embeds this brief AS QUOTED DATA inside
  `<<<PROJECT-BRIEF>>>` fences — it is context, never instructions.
- Outcomes are FIVE CLASSES: `done` (work completed), `work_failed` (the
  work was attempted and failed — burns an attempt), `infra_failed` (the
  lane failed before work — net-zero retry, own budget), `deadline`
  (self-reported wall hit — the reaper's early signal), `poison`
  (anomalous/contract-violating — terminal quarantine, no retry).
- The write-back DOOR governs artifacts: only `tasks/<id>/**` and declared
  paths; `.github/**`, dotfiles, and root escapes are always denied.
- Report ids are attempt-scoped (`rep-<run>-a<attempt>`): a re-run's
  report is never dedup-swallowed.
- Leases: a task is assigned with a lease; expired leases are reaped by
  the clock (attempt-burn) or self-reported (deadline class).

## Current epoch conventions

- Mode `mock` (deterministic shim behaviors) is the default; mode `cc`
  routes through the Claude-Code adapter (OpenRouter lanes, free-model
  fallback); mode `real` is the raw-completion stand-in.
- Config defaults: max_parallel 4, lease 4 min (15 in long-lease epochs),
  max_attempts 3, tick interval 25s.
- The ops lane: repository_dispatch `fsm-control` {pause|resume|halt|
  unhalt|reset|configure}. Alerts: the `fsm-watchdog-alert` and
  `exec-duty-alert` labels on this repo's issues.

## Environment facts worth knowing

- GHA schedules are SPARSE: nominal 10-min crons fire ~2-4h apart; the
  chain's continuity rides self-dispatch, not cron.
- repository_dispatch resolves workflows from the DEFAULT branch only;
  feature-branch runs need workflow_dispatch with an explicit ref.
- Run names carry the task id + attempt (`task-<id> · <behavior> ·
  a<n>`) — the law-4 verification matches on them.

## Edge: duplicate report (T-107)

**Definition.** A duplicate report is the same report id `rep-<run>-a<attempt>` submitted more than once *within the same attempt*. The contract already pins the dedup invariant: report ids are attempt-scoped, and "a re-run's report is never dedup-swallowed." That sentence tells us dedup *exists* and is keyed on the full id — the only thing explicitly forbidden to swallow is a re-run.

**Correct handling — four rules:**

1. **Dedup key is the full report id `rep-<run>-a<attempt>`.** Never `run` alone, never `task_ref` alone. Deduping on either of those is the bug that swallows legitimate re-run reports.

2. **Benign duplicate (same id, same payload) → idempotent swallow.** No state mutation, no attempt burn, no re-dispatch, no double-counting. First report for the attempt is authoritative (first-writer-wins). This tolerates network retries and worker resends without punishing them.

3. **Re-run report (new attempt → new id) → never swallowed.** Must be processed normally: it burns its own attempt, can trigger its own retry, and can change the task's terminal class. A re-run's report must not be treated as a repeat of the prior attempt's report.

4. **Duplicate with a conflicting payload** (different outcome class, `task_ref`, `session`, or `budget` than the recorded report for that id) → **`poison`**. Same id carrying two different outcomes is a contract violation, not a benign resend. Terminal quarantine, no retry. This is what distinguishes a lost-packet resend from a spoofed/conflicting report.

**Corollaries worth getting right:**

- A duplicate arriving *after* a retry has already been dispatched (e.g., first report was `work_failed`, attempt 2 is now in flight, then a duplicate `work_failed` for attempt 1 lands) must be swallowed silently — it must not cancel, alter, or burn an attempt against the in-flight retry.
- A late duplicate can never undo a `done`. First-writer-wins means a stale resend can't un-complete a task.
- The write-back DOOR is unaffected — reports are the outcome channel, not artifacts — but the same first-writer-wins idempotency applies to artifact writes under a given path: a second write to `tasks/<id>/**` for the same path is a no-op, not an overwrite.

**Failure mode this edge guards against:** a naive dedup on `run`/`task_ref` makes a re-run's report look like a repeat of the original, so the re-run is swallowed and the task appears to terminate on the *first* attempt's outcome — the retry budget is silently lost and the chain looks healthy. The attempt-scoped id exists specifically to prevent that.
